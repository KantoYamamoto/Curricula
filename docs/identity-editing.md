# UUID、編集版、分割・統合の運用

確認日：2026-10-11。対象のUUIDと編集版を分け、修正・分割・統合の履歴と根拠の版固定を扱う。[契約0.2.0](exchange-contract-0.2.md)が基準。[SQLite編集](local-editing.md)は新規対象・目標と本文・条件・注釈・根拠を扱い、分割・統合のUIは未実装。共通Swift操作と回帰標本は維持する。

## Swiftの手動標本でIDを発行する

```sh
python3 scripts/allocate_identity.py goal.example
python3 scripts/allocate_identity.py goal.example --revision 2
```

初回にUUIDv4の対象IDと編集版を発行して登録簿へ保存する。同じキー・同じ編集版番号への再実行は同じ値を返す。次の編集版番号では対象IDを維持し、新しい編集版UUIDだけを発行する。ビルド中は登録済みのIDだけを使用し、不足するキーを検出したら失敗する。

登録簿のキーは入力を書くための固定キー。表示名を変えるたびにキーを変えない。公開データの `aliases` は別の索引で、改称後も旧別名を残せる。同じ対象が複数の別名を持っても関係や根拠の参照UUIDは変わらない。

## 編集・分割・統合

[EditorV2.apply](../Sources/Curricula/EditingV2.swift) はメモリ上のスナップショットを受け取り、検証に成功した新しいスナップショットを返す。失敗時に入力は変更しない。

| 操作 | 指定するもの | 結果 |
|---|---|---|
| edit | 期待する旧ID＋編集版、同じIDで新編集版を持つレコード | 同一対象を編集し、旧公開版は保存 |
| split | 一つの旧対象、新IDの複数対象、旧対象の廃止編集版 | 旧IDをretiredにし、複数の後継を登録 |
| merge | 複数の旧対象、新IDの統合対象、旧対象それぞれの廃止編集版 | 旧IDから同じ統合先を追跡 |

全操作に新しい公開版、変更レコードのID＋編集版、理由を渡す。期待する旧編集版が現在のレコードと違えば競合として拒否する。過去と同じ編集版UUIDで内容を書き換えた場合も検証で拒否する。

目標を編集すると、その目標の旧編集版に結び付いた注釈・根拠は自動で付け替えない。`annotationUpdates` と `evidenceUpdates` で更新するレコードと新しい編集版を明示し、同じ操作で検証する。更新し忘れると `staleRevision` になる。意味が変わった目標へ古い根拠を無条件に流用することを防ぐ。

分割・統合後の原典対応、前提、目次は勝手に複製しない。操作例では目次に旧対象を残して後継を案内する。新しい対応や経路を採用する場合は、それらも明示的に編集し、公開時に全体を検証する。

## 再現できる例

`swift run curricula export-v2 data/releases` は次の操作例を生成する。

- `editing-0.2.0`：元の7目標、Aまたは(BかつC)の前提式、3種類の出典。
- `editing-0.2.1`：経路Aの文言を変更。対象UUIDは同じ、編集版UUIDは別。
- `editing-0.2.2`：「説明と図示」を二つの新しい目標へ分割。旧対象と後継一覧を保存。
- `editing-0.2.3`：「資料を読む」「資料を比較する」を新しい目標へ統合。二つの旧対象から追跡可能。

各版の `/changes` と対象詳細で、旧新版の本文へたどれる。読書画面・構造画面から旧対象の後継にも移動できる。

## SQLite編集と原典取り込みのID

SQLiteの新規作成はUUID v4を発行してDBへ保存するため、上記の登録簿への手動追加は不要。対象と不変の改訂・版集合を分け、期待する下書き版をトランザクション内で照合する。[保存と競合の仕様](local-editing.md)を参照。ローカル編集では未確認の古い根拠を残して下書き保存できるが、そのまま確認・版作成はできない。Swiftの `EditorV2.apply` は検証済みスナップショットを返すため、その時点で古い改訂を拒否する。

新規の原典自動取り込みは固定名前空間と原典コードからUUID v5を生成し、再生成しても対象IDを変えない。既存小標本と重なる原典は登録済みUUIDを引き継ぐ。原典の内容が変われば改訂UUIDを変える。コード変更・分割・統合を同一対象と推測して自動付け替えはしない。[原典の識別](curriculum-coverage.md)を参照。

登録簿の同時編集を共同編集基盤として使わない。公開wiki編集の認証・権限・運用は未実装で、UUIDの発行だけを競合解決とみなさない。
