# wiki編集とDB移行の方針

> 2026-10-04：[ローカルSQLite編集](local-editing.md)を実装。5版の試験投入・書き戻し、下書き編集、競合検出、版へ固定した確認記録、版作成、バックアップ復元まで確認。以下の未導入という記述は初期方針の履歴。現在は編集起動時にDBを保存元とし、公開運用・認証・役割・構造の編集UIは後続工程。

更新日：2026-09-28。ユーザーの「将来wikiのように文言・観点を編集したい場合に備える」という方針を記録する。現在は移行を見据えた設計段階で、DB・編集画面・ユーザー管理を今回導入する決定ではない。採用製品、公開運用、編集権限は未決定。

## 目指す役割分担

```text
編集画面 → 編集API → DBの下書き・編集履歴
                       ↓ 共通モデルへの変換
                    機械検証・内容レビュー
                       ↓ 公開対象のリビジョンを固定
                 不変の版付きJSON → 読み取りAPI → 二つの閲覧画面
```

コードにはモデル、検証ルール、入出力、API、画面を置く。DBには文言、説明、能力の条件・達成観点、対象間の関係、目次、出典対応、編集履歴とレビュー状態を置く。公開JSONは配布・再現用のスナップショットとして残す。DBを導入しても、公開APIの利用者に編集途中の状態を直接見せない。

今はSwift宣言が独自データの正本、JSONは生成物。移行後はDBを編集データの正本にし、Swiftの小標本は初期投入・回帰検証用にする。SwiftとDBを同時に編集可能な二つの正本にしない。編集用DBの設計と外部JSON契約は同一にする必要はなく、変換層を通じて同じ意味を維持する。

## 保持する境界

- **原典と独自編集**：取り込んだ原文・配布版・ハッシュ・引用位置を保存し、通常のwiki編集では上書きしない。訂正や再取り込みは新しい原典版として差分を確認する。説明、解釈、能力、対応付けは別の編集対象にする。
- **対象のIDと編集版**：安定IDは画面上の位置・ラベル・DBの連番から独立させる。同じ対象の文言修正は同じID＋新リビジョンで残す。定義の変更や分割・統合は新IDと対応理由を伴う移行として扱う。
- **下書きと公開版**：公開版が参照する原典・対象・関係・目次のリビジョン集合を固定する。公開後にDBのラベルを書き換えても旧版のJSON・API・根拠が変わらないようにする。
- **機械検証と内容レビュー**：検証成功で内容を自動的にレビュー済みにしない。内容変更後は以前のレビューをそのまま流用せず、対象リビジョンと確認範囲を照合する。
- **枠組み・対象・能力・編成**：DB化を理由に原典階層・学ぶ対象・学習前提・目次順を一つにまとめない。機関・年度・学習経路の文脈、部分対応・対象外・未調査を保持する。

## DBで必要になる概念（テーブル設計は未確定）

| 概念 | 主な保持内容 |
|---|---|
| 原典と取得版 | 発行主体、資料種別、URLまたはローカル由来、適用範囲、配布版、取得記録、ハッシュ、原文 |
| 枠組み・対象・能力・関係・目次 | 安定IDと各リビジョン。外部コードは名前空間・機関・版に紐付ける |
| 編集履歴 | 編集者、時刻、変更理由、変更前後または親リビジョン、変更対象 |
| レビュー | 対象リビジョン、確認者、観点、結果、指摘と対応 |
| 公開版 | 公開対象のリビジョン集合、スキーマ版、検証結果、生成物のハッシュ |
| 移行対応 | 旧版・新版本体のID、分割・統合・廃止・定義変更などの種類、根拠、未対応範囲 |

リレーショナルDBを第一の構成候補とし、多対多の関係と参照整合性を表せる形を検討する。関係が多いことだけを理由にグラフDBを必須にしない。柔軟なJSON列の利用は可能だが、ID・参照・版・編集履歴の重要な制約をすべて自由形式の文章に逃がさない。具体製品は編集者数・ホスティング・運用負荷が見えてから選定する。

## 最初の編集機能で確認すること

同じ版を二人が編集した場合は、保存時に元リビジョンを照合し、後から保存した人が他方を黙って上書きしない。編集者・レビュー担当・公開担当の権限と変更理由を記録する。対象削除は参照を壊す物理削除ではなく、廃止・後継先を含めて扱う案とする。

公開は原典・対象・関係・目次を一貫したスナップショットで検証してから行う。検証後に編集が進んでも、公開するリビジョン集合を変えない。編集APIと読み取りAPIは責務を分け、現在の外部非公開・読み取り専用という境界を、編集機能の実装だけで無断に変更しない。

## 段階的な移行案

1. **小標本で契約を検証**：正常例・不正例・未対応例を用意し、DB化前に欠けている概念を把握する。[検証カタログ](sample-catalog.md)を参照。
2. **読込・出力の境界を設ける**：Swift宣言、JSON、将来のDBから同じ共通モデルへ変換し、共通の検証と正規形出力を使う。DB製品固有の型を交換契約へ漏らさない。
3. **試験DBへの投入と書き戻し**：現在のID・原文・条件・出典・対応を欠落なく移し、DBからの出力が既存JSONと一致することを確認する。非対応フィールドの黙殺を避ける。バックアップと復元も確認する。
4. **下書き編集・競合・レビューを実装**：まず少数の項目で操作を検証。分割・統合などの意味変更は文言修正と別操作にする。
5. **正本を切り替える**：移行結果を照合してからDBを正本にする。切替前の入力と公開版を保存し、戻せるようにする。Swift小標本は回帰テストとして維持する。

移行の受入条件は、旧版再現、IDと意味の保持、原典再取込で独自編集を破壊しないこと、競合検出、レビューの版紐付け、参照・部分対応・文脈・履歴の欠落がないこと。同時編集・認証・履歴管理は現行実装の機能ではない。

## 教科横断の標本から引き継ぐ項目

[8教科・11例の検証](cross-subject-validation.md)から、学年帯・教科・科目の検索属性と、編集した各条件・観点から原典項目のリビジョンへの根拠参照を追加候補とする。親項目に含まれる条件をどの範囲で継承するかも、暗黙の文字列処理にせず仕様にする。

補助ケースでは資料種別ごとの必須メタデータ、分割・統合等の改訂対応、AND/OR経路が未対応と分かった。これらは保存先をDBに変えるだけでは解決しないため、交換契約と共通検証の拡張として扱う。

## 2026-09-29 共通契約の更新

[契約0.2.0](exchange-contract-0.2.md)と[ID・編集操作](identity-editing.md)を実装した。DB移行時はこの契約を基準にする。

- 学校段階、学年指定の状態と学年集合、教科・科目UUIDを検索属性にする。
- 対象UUIDと編集版UUIDを分離し、別名は別索引へ置く。分割・統合は変更イベントと旧対象の後継一覧を持つ。
- 根拠は編集対象のフィールドと原典の両方を編集版へ固定する。判定の観点は独立した自然言語注釈として目標へ固定する。
- AND/OR式と文脈を保持し、単純な辺一覧へ変換しない。資料種別に応じた書誌・告示・取得情報を任意項目として持つ。
- ローカル編集操作は期待する旧編集版を照合する。DB実装時はこの条件をトランザクション内で検証して更新する。

以上はDBへ移す前に共通モデルと公開JSONで検証済みの境界。DB製品・認証・編集UIの導入は別工程とする。
