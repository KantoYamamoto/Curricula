# 要件整理 v0.3

状態: 改訂可能な作業仮説 / 更新日: 2026-09-28

## 1. 長期の目標と現在の方針

小中高校から大学教養まで、学ぶ対象・能力・教育上の要求を結び、開発者やAIが再利用できるデータ基盤を目指す。個人の自学を最初の利用場面とする。

Swiftの宣言的記述、JSON等の出力、ローカルMVP、OSS、AI下書きと段階的なレビューは現在の方針。永久固定の要件ではない。変更履歴と見直しの条件は[方針台帳](decisions.md)に記録する。

## 2. 長期設計とMVPの分離

| 区分 | 扱う範囲 | 完了の意味 |
|---|---|---|
| 長期の収録目標 | 小中高校・大学教養 | 機関・版・分野の範囲を定義して拡張する。今は全体網羅を宣言しない |
| MVPの内容整備 | 比例の意味と表・式・グラフの対応、および小学校までの関連前提 | 選定した部分の出典・能力・関係をレビューできる |
| MVPの構造検証 | 高校、大学、異なる枠組み・条件・定義の少数例 | 学年や文科省コードを必須にせず、同じ構造で記述・出力できる |

MVPの単元はユーザーの委任によりアシスタントが選定した案。選定理由・対象外・切替条件は[単元選定](pilot-scope.md)に記す。カリキュラムの構造表示と、指導要領・知識・能力を教科書風に読む別ページを含める。両者は読み取りAPIを利用する。問題実行、学習記録、習熟度、自動推薦、インターネットへのAPI公開は当面対象外。レビューは小標本・構造・画面・内容の段階ごとに行い、専門家の確保を条件にしない。

## 3. 要件候補と確認方法

IDは旧版から追跡し、内容をv0.3に改訂している。将来の受入条件であり、現在合格済みという意味ではない。

| ID | 要件 | 確認方法 |
|---|---|---|
| F01 | 出典と版を識別 | 告示・適用期間・原典訂正・配布データ版・取得日を別に保持 |
| F02 | 枠組みの項目と階層を参照 | 指導要領と大学の項目を、発行主体・出典付きで区別 |
| F03 | 学ぶ対象と能力を独立定義 | 同じ比例を対象に「読み取る」「説明する」の複数能力を定義 |
| F04 | 要求と知識・能力の対応 | 多対多、部分対応、未対応、参照元の違いを保持 |
| F05 | 関係の意味と根拠 | 学問上の関係、学習前提、履修規則、原典階層を混同しない |
| F06 | 機械検証と内容レビュー | 参照切れ等を検出し、教育上の妥当性のレビュー状態とは分離 |
| F07 | 版付きローカル出力 | 同じ入力から同じ論理データを出力し、変更履歴を確認 |
| F08 | 利用例 | 能力→対象→原典、枠組みを指定した対応、条件を指定した前提を取得 |
| F09 | Swift以外からの参照 | JSONでID・版・関係の意味を再現 |
| F10 | Swift宣言API | 表示ラベルや記述順を変えてもID・意味が変わらない |
| F11 | 小学校までの関連前提 | 選定単元に必要な経路を根拠付きでたどり、調査境界を明示 |
| F12 | 教育段階・機関に依存しない中核 | 学年なし、文科省コードなし、複数課程に現れる同一対象を扱える |
| F13 | 文脈・定義・条件の違い | 同名でも異なる対象や、同じ対象に対する異なる能力を自動統合しない |
| F14 | 改訂可能な仕様 | 設計の変更理由・代替案・移行対象・受入条件の変更を追跡 |
| F15 | 独立した読み取りAPI | 構造表示・閲覧ページが共通の版付きデータをAPIで取得 |
| F16 | 二つの表示 | 枠組みの階層と対応を見る構造画面、章・節に沿って読む閲覧ページを分離 |
| F17 | 段階的なレビュー | 対象の版・確認者・観点・指摘・対応を記録。専門家の有無を完了条件にしない |

## 4. 原典の選び方

最新＝取得時点の公式な告示済み原典と該当する訂正、とする作業上の解釈。次期改訂の審議資料は別種の資料として区別する。調査時点の文科省掲載は小中学校が平成29年、高校が平成30年告示。具体的ファイル・コード表・訂正の一致は取り込み工程で再確認する。[文科省の掲載一覧](https://www.mext.go.jp/a_menu/shotou/new-cs/1384661.htm)

「latest」という参照だけを保存せず、取得時点のURL・版・日付・内容ハッシュ等を記録する案。新しい原典が出ても、旧版を上書きせず対応を見直す。大学は各機関のカリキュラムや参照基準の版を識別する。

## 5. 品質と完了条件

1. 比例の対象原典と収録範囲が一覧化され、反比例など未収録部分を完全対応と誤表示しない。
2. 知識・能力・前提に根拠または編集上の理由とレビュー状態がある。
3. 小学校までの関連前提について、基礎まで到達・対象外・未調査を区別する。
4. ID重複・参照切れ・禁止された循環を検出し、許される関連の循環を拒否しない。
5. Swift記述→検証→JSON→API→構造表示・閲覧ページがローカルで再現できる。
6. [構造検証例](architecture-cases.md)で、大学の項目に架空の学年・文科省コードを補わず表現できる。
7. 内容の確認と技術的整合性の結果を分け、実施した段階的レビューと未確認事項を記録する。専門家レビューは当面の工程に置かない。
8. Swiftや分類法の負担を記録し、継続・改善・変更の判断材料を残す。

数学の正しさを一般に自動証明する仕組みや、全分野を矛盾なく表現できる保証はMVPの達成条件にしない。矛盾や分類不能な事例が見つかったら、隠さず境界・条件・モデルを修正する。
