## 2. 初期成果

比例と小学校までの関連前提をSwiftで宣言し、検証してJSON・読み取りAPI経由で構造表示と教科書風の閲覧ページに表示するローカルMVP。高校・大学・異分野の合成例も同じ中核で記述できるか確認する。大学側の合成例を実在する到達目標と表示しない。

原典コードの有無や学年によってモデルを分岐させすぎず、教育文脈と学ぶ対象を分離する。構造表示と閲覧ページを別に設け、共通の読み取りAPIから取得する。[閲覧・API仕様](viewer-api.md)を参照。専用レビュー管理画面、Markdown出力、インターネットへのAPI公開、問題実行、学習記録・習熟度は当面の実装範囲にしない。

## 3. 構成案

```text
Swift宣言 + 版を固定した原典入力
        ↓
共通モデル（枠組み・対象・能力・関係・文脈・出典）
        ├─ Validation → 問題の場所と理由
        └─ 版付きJSON → 読み取りAPI → 構造表示 / 教科書風の閲覧ページ
```

Swift Packageのライブラリと実行用ツールは構成候補。最初は小さな宣言APIを使い、Result Builderを導入する場合も同じ共通モデルを組み立てる補助とする。パッケージ名・ターゲット数はまだ固定しない。

記述案（未実装の擬似コード）:

```swift
Competency(
    id: "cp.link-signed-representations",
    label: "負の値も含む比例を表・式・グラフで関連付ける",
    targets: ["sm.proportional-relation"],
    conditions: "与えられた比例関係。入力範囲と係数を明示する",
    reviewStatus: .draft
)
```

型・ID形式・引数名は検討用。コンパイル可能な納品コードではない。枠組みへの対応はこの能力とは別のAlignmentで記述する案。

## 5. 実装・検証上の注意

- 内部IDと名前空間付き外部コードを分ける。文科省コードの形式を全IDに強制しない。
- Swiftのenumに全教科・全学年・全知識IDを閉じ込めない。分類語彙には版・拡張方針を持たせる。
- JSONは明示的な交換契約にし、Swift型の自動符号化が偶然生成した形をそのまま恒久仕様にしない。
- データ構築を現在時刻・乱数・実行中のネットワークに依存させない。変動メタデータは別扱い。
- 原典の再取り込みで独自の能力・対応・レビューによる修正を上書きしない。
- Validation本体はSwift Testingに依存しない通常の処理とし、テスト側から呼び出す案。
- 機械検証と内容の確認を区別する。専門家レビューは当面要求しない。
- 元の原文、要約、独自の解釈、合成例を識別する。

## 6. 受入確認の代表例

| 入力 | 期待する振る舞い |
|---|---|
| ラベル変更、記述順変更 | 安定IDと意味を維持 |
| 重複ID、参照切れ | 対象の場所と理由を報告 |
| 同文脈の厳密な必須前提が循環 | 経路を報告 |
| 関連の循環、異なる立場の併記 | それだけで不合格にしない |
| 比例・反比例の原典に比例のみ対応 | 部分対応、対象外・未収録部分を保持 |
| 学年なし、文科省コードなしの大学項目 | 不正なダミー値を補わず受け入れる |
| 同名で定義条件が違う知識 | 自動統合せず別ID・関係で扱える |
| 同じ入力から再出力 | 定義した正規形で一致 |
| 原典項目の分割や機関別対応 | 旧版を保持し、移行先・根拠をたどれる |
| 過去の方針変更 | 元の理由と変更後の影響を追跡できる |

タスクの完了報告では、実施した確認、段階的レビューの実施範囲と未確認事項、未対応のモデル、次に見直す事項を区別する。少数例の合格から全分野対応を宣言しない。
