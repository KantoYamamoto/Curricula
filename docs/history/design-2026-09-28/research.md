## 5. 習熟度・学習支援の先行研究

### R01 — Bayesian Knowledge TracingとpyBKT

Badrinath, Wang, Pardos (2021), *pyBKT: An Accessible Python Library of Bayesian Knowledge Tracing Models*。[論文](https://arxiv.org/abs/2105.00385)、[学会公開本文](https://educationaldatamining.org/EDM2021/virtual/static/pdf/EDM21_paper_237.pdf)。本文冒頭のモデル定義と概要を確認。

観測された正誤と潜在的な習得状態を分け、初期習得・学習・当て推量・誤答のパラメータを扱う。標準モデルには忘却しない仮定がある。

**設計への提案:** 正答率をそのまま「理解度76%」と呼ばない。能力と問題の対応、回答順序、支援の有無、推定モデルの版を保持する。BKT採用は未決定で、任意の初期値を入れただけで妥当な習熟度が得られるとは扱わない。

### R02 — 初回回答と学習後の回答を分けて評価する

Zhang et al. (2021), *The Cold Start Problem and Interpretation of Knowledge Tracing Models’ Predictive Performance*。[学会掲載の要旨](https://educationaldatamining.org/EDM2021/virtual/poster_paper126.html)を確認。

初回の新しいスキルへの予測と、練習後の予測は意味が異なることを検討している。

**設計への提案:** 将来のモデル比較では、履歴の少ない利用者・能力を分けて評価する。この論文から、全教科に共通する必要回答数を決めることはできない。

### R03 — 評価方法によってモデル性能を過大評価し得る

Liu et al. (NeurIPS 2022), *pyKT: A Python Library to Benchmark Deep Learning based Knowledge Tracing Models*。[著者公開の要旨](https://arxiv.org/abs/2206.11460)を確認。

前処理・評価手順の不統一と、ラベル漏洩による性能の過大評価を扱う。

**設計への提案:** 深層学習の導入を初期目標にしない。将来は予測対象を定義し、学習者・時間・問題の関係を考慮したデータ分割、単純モデルとの比較、確率の校正を検討する。予測精度と学習効果は別に評価する。

## 7. Swiftによる記述・検証・出力

ユーザー方針: Swiftで宣言的に記述し、JSON等にも出力する。まずローカルで検証し、MVP後にSwiftの不都合を評価する。

| ID | 公式資料 | 確認事項と適用案 |
|---|---|---|
| S13 | [Swift Package Manager](https://docs.swift.org/package-manager/PackageDescription/PackageDescription.html) | ライブラリと実行可能な製品を構成できる。共通モデルと検証・出力ツールの構成候補 |
| S14 | [Swift resultBuilder](https://docs.swift.org/swift-book/ReferenceManual/Attributes.html)・[AppleのDSL解説](https://developer.apple.com/videos/play/wwdc2021/10253/) | 宣言的なDSLを作る言語機能がある。通常の初期化構文で意味を確かめてから、記述の繰り返しを減らす用途に使う案 |
| S15 | [Foundationのシリアライズ](https://developer.apple.com/documentation/foundation/archives-and-serialization) | Codable等を使う符号化・復号の仕組みがある。内部型と外部JSONの互換性規則は独自に設計が必要 |
| S16 | [Swift Testing](https://developer.apple.com/documentation/testing)・[テスト関数の定義](https://docs.swift.org/latest/documentation/testing/definingtests/) | Swift Packageの検証に利用できる。Testingのimportはテストターゲット等に限定する推奨がある。配布用のValidator本体はTestingへ依存させない案 |

ローカル確認: `swift --version` はApple Swift 6.4、arm64 macOSを返した（2026-09-28）。これは当該環境の確認で、公開ライブラリの最低対応バージョンの決定ではない。

**設計上の提案:** Swift記述→共通のデータモデル→意味の検証→交換用データ、という流れにする。知識や能力の全IDを閉じたenumにすると追加のたびにライブラリの変更が必要になるため、型付きIDとデータを分ける案を比較する。コンパイル成功だけでは参照切れや教育上の誤りは検証できない。

MVP後の評価軸: 小標本の記述量、エラーメッセージの分かりやすさ、データ拡大時のビルド時間、段階的レビューのしやすさ、他言語からの利用、実行環境の制約。デメリットが具体化する前に別言語へ変更しない。

### 最新版の扱いで見つかった注意点

学習指導要領の告示年、コード表の修正版、LODの個別項目の出典版は同じものではない。S01の小学校コード表に82V12が掲載される一方、S22の小学校の個別ページは82V11を出典としている。これは直ちに本文の相違を意味しないが、取り込み前の差分照合が必要な例になる。

### 今回の調査の限界

大学の参照基準や一大学の科目一覧を、全大学の必修要件や一般的な教養の完全な一覧とは扱わない。大学の具体的な到達目標と前提関係の取り込み、比例の学習前提に関する実証研究の精読、専門家レビューは今後の工程。現在の高校・大学・異分野の例は、モデルの制約を検証するための合成例である。
